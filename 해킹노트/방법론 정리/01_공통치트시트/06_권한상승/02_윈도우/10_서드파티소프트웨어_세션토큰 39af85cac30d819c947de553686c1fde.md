## 1. 설치된 서드파티 소프트웨어 열거 → 로컬 익스플로잇 검색

winPEAS가 설치된 소프트웨어 목록을 자동으로 나열해주지만, 그 목록을 보고 "이 소프트웨어 이름으로 알려진 로컬 익스플로잇이 있는지"는 사람이 직접 판단해야 한다. 구버전/니치한 백업·모니터링·원격관리 툴이 SYSTEM 권한으로 돌아가는 스케줄러/서비스를 가진 경우가 많아서, 이런 소프트웨어를 보면 먼저 이름+버전을 확인하고 검색하는 습관이 필요하다.

```powershell
# 설치된 소프트웨어 목록 (레지스트리 기반, 빠름)
Get-ItemProperty "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\*" | Select-Object DisplayName, DisplayVersion
Get-ItemProperty "HKLM:\SOFTWARE\Wow6432Node\Microsoft\Windows\CurrentVersion\Uninstall\*" | Select-Object DisplayName, DisplayVersion

# wmic (구버전 호환성 높음)
wmic product get name,version
```

```bash
:: 폴더 직접 훑기 (GUI로 보면 더 빠름)
dir "C:\Program Files"
dir "C:\Program Files (x86)"
```

### 수상한 소프트웨어 발견 시 이어지는 순서

```
1. 이름 + 버전 확인 (설치 경로의 실행파일 속성, 또는 실행 시 나오는 버전 정보 창)

2. 로컬 익스플로잇 검색
searchsploit <소프트웨어명>
구글: "<소프트웨어명> <버전> privilege escalation exploit"

3. 서비스/포트 확인 (이 소프트웨어가 어떤 권한으로 돌고 있는지)
Get-CimInstance -ClassName win32_service | Select Name,State,PathName | Where-Object {$_.PathName -like '*<소프트웨어경로>*'}
netstat -ano
Get-Process -Id <PID>

4. 가장 흔한 패턴: 스케줄러/트리거된 작업을 "다른 계정으로 로그인" 설정 없이 돌리는 경우
→ 그 뿐이면 서비스/스케줄러 자체 권한(보통 SYSTEM)으로 실행됨 → 내가 지정한 스크립트/프로그램이 그대로 SYSTEM 권한으로 실행됨
```

### 실제 사례 — Sysax Automation Suite 6.90 (Exploit-DB 50834)

Sysax의 Triggered Task 기능이 "특정 폴더에 파일이 추가되면 지정한 프로그램 실행"을 지원하는데, "Login as the following user to run task" 체크를 해제하면 Sysax 스케줄러 서비스 자체 권한(Local System)으로 그 프로그램이 실행된다. 낮은 권한 유저가 이 설정을 만질 수 있다는 것 자체가 취약점.

```
1. 트리거될 배치파일 생성 (예: net localgroup administrators <내계정> /add)
2. sysaxschedscp.exe -> Setup Scheduled/Triggered Tasks -> Add Task (Triggered)
3. Monitor folder 지정, "Run task if a file is added" 체크
4. Run any other Program -> 위 배치파일 경로 지정
5. "Login as the following user to run task" 체크 해제   <- 핵심
6. Save -> 감시 폴더에 아무 파일이나 추가해서 트리거 발동
```

## 2. 그룹 멤버십 변경 후 재로그인 필요 (토큰 갱신 안 됨)

Windows는 로그인할 때 "이 사용자가 어떤 그룹에 속하는지"를 토큰에 고정시킨다. 로그인 이후에 그룹을 바꿔도(예: 지금처럼 임의로 administrators에 추가된 경우), 그 세션은 여전히 "변경 전" 상태의 토큰을 들고 있다 → 로그아웃 후 재로그인해야 새 그룹 권한이 반영된다.

```powershell
# 변경 전 확인 (이 결과가 안 나온다면 아직 반영 안 된 것)
net localgroup administrators

# 재로그인 후 확인 (이때는 정상적으로 나와야 함)
whoami /groups | findstr Admin
logoff
```

## 3. UAC deny-only 토큰 분할 (관리자 그룹인데도 권한 없음)

재로그인을 해도, 일반 프로세스(cmd, PowerShell)를 그냥 열면 UAC가 관리자 권한을 자동으로 필터링해서 일반 유저 권한으로만 실행된다. 명시적으로 "관리자 권한으로 실행"해야 실제 권한이 활성화된다.

```powershell
# 지금 대상이 deny only인지 확인
whoami /groups | findstr Admin
# "Group used for deny only"가 보이면 권한이 필터링된 상태

# 해결 — 시작 메뉴 -> 우클릭 -> "관리자 권한으로 실행"
# 또는 현재 세션에서
Start-Process powershell -Verb runAs
```

## 4. WinRM 권한 ≠ RDP 권한 (별도 그룹)

WinRM(evil-winrm 등)은 기본적으로 로컬 Administrators 그룹 또는 "Remote Management Users" 그룹 멤버만 허용한다. "Remote Desktop Users" 그룹(RDP만 허용)에만 속한 계정은 RDP는 되지만 WinRM은 `WinRMAuthorizationError`로 거부된다. 또한 방금 로컬 관리자 그룹에 추가된 계정이라도, UAC 원격 토큰 필터링(`LocalAccountTokenFilterPolicy`)이 기본값(0)이면 원격 WinRM/WMI 접근 시 관리자 권한이 동일하게 필터링되어 실패할 수 있다 (위 UAC deny-only와 같은 원리가 원격에서도 적용됨).

```
WinRM::WinRMAuthorizationError
```

```powershell
# 관리자 세션에서 이 계정을 명시적으로 Remote Management Users에 추가
net localgroup "Remote Management Users" /add <계정명>

# 또는 UAC 원격 필터링 자체를 해제 (로컬 관리자 그룹 전체가 원격 접근 가능해짐)
reg add HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System /v LocalAccountTokenFilterPolicy /t REG_DWORD /d 1 /f
```

WinRM/evil-winrm이 거부되면, 이 권한 설정을 바꿀 수 없는 상황(아직 낮은 권한)에서는 RDP 드라이브 리다이렉션(`\\tsclient\`)으로 파일을 주고받는 우회가 실용적이다 (04_파일전송/Linux_to_Windows 참고).

## 팁

- WinRM 거부 → 바로 포기하지 말고 "이 계정이 어느 그룹에 있는지" 확인부터 (RDP만 되는 계정일 수 있음)
- 그룹 추가 직후 권한 안 적용되면 → 바로 재로그인부터 (토큰 갱신 문제)
- 재로그인해도 권한 안 되면 → "관리자 권한으로 실행" 했는지 확인 (UAC deny-only)
- 낮은 권한 상태에서 낯선 서비스/소프트웨어를 발견하면 이름+버전으로 공개 익스플로잇부터 검색할 것 — GTFOBins에 없다고 포기하지 말 것
